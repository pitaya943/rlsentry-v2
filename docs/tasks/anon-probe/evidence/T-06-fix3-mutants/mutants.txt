## S18/S19 (several writes: the first, or the last, read): the reason, completed
Equivalent. A request's log holds the plans of its own top-level statements only: auto_explain's
log_nested_statements is off (rlsentry/sandbox.py sets only log_min_duration, log_analyze,
log_timing, log_format and log_verbose for authenticator, and log_nested_statements is
superuser-only, so no migration can turn it on). So a trigger's or a policy function's own write
to the table never adds a second ModifyTable. What else could: PostgREST's write sits in a WITH,
where PostgreSQL refuses DO ALSO rules (fix 2 probe `also`), and an INSTEAD rule doing the same
operation on the same table recurses (probe `recur`); so the request holds PostgREST's own write
alone, or rule writes none of which is the requested operation on public.<table>, which S20
refuses whichever is read.
Pinned: test_the_requests_plan_holds_only_its_own_statements_write sends a PATCH to a table whose
AFTER UPDATE trigger runs its own UPDATE on the table, and expects one ModifyTable in the request's
plans. N1 (log_nested_statements turned on for authenticator) fails it: assert 7 == 1.
