# T-02: Insert, update and delete attacks

Status: open
Risk: high (mutating requests; the guard must still hold for them)
Scenarios: S-2, S-4
Depends on: T-01
Areas: `rlsentry/attacker.py`, `rlsentry/sandbox.py` (restore, superuser confirmation), lab

## What
Design §4: insert, update, delete through PostgREST as anon. Update and delete success is
confirmed through the sandbox's superuser connection. The table is restored after each
destructive attempt so operations do not hide each other. Lab gains `lab_insert_only`,
`lab_update_open`, `lab_delete_open` and `lab_owner_only` (correct `auth.uid() = user_id`
policies; a minimal `auth.uid()` returning null for anon is enough here, the full stand-in is
T-03). `expected.json` gains all four operations for every lab table.

## Check (fails today: only READ is judged)
- Lab integration asserts, per table and operation, exactly `expected.json`. In particular
  `lab_insert_only`: INSERT EXPOSED with the created row as evidence, UPDATE and DELETE
  protected; `lab_no_policy` and `lab_owner_only`: all four protected.
- A test where an update policy hides rows (`using (false)`) is judged protected although
  PostgREST answers 2xx with 0 rows.
- After a full lab run, a superuser row count shows each table back at its seeded state
  before teardown (restore works).
