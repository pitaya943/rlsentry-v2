## What

from seeded values, constants in that table's policy expressions and CHECK constraints
(`pg_policies`, `pg_constraint`, read by the sandbox, not the attacker), enum labels, and
`null`. The report names the source that succeeded, or `protected (N rows tried)`. Lab gains
`lab_value_policy` (`with check (status = 'pending')`). `expected.json` covers all eight
design §5 tables.

## Added after T-03's verification (PR #5 PASS verdict, Finding 1)
Migrations and seeding run as a real PostgreSQL superuser, so a migration file can reach
the host through SQL: `copy (select 1) to program 'touch /tmp/x'` and
`copy (...) to '/path'` both succeed (as OS user `postgres`), exit 0. This is the SQL-level
member of T-03's D2 class ("nothing in a migration file may touch the host"), and it predates
T-03. Hosted Supabase refuses it: its `postgres` role is not a superuser.
- Fix the class: migrations (and anything else that runs migration-authored code, such as
  triggers fired during seeding) run as a non-superuser role shaped like hosted Supabase's
  `postgres` role, not the cluster superuser. The superuser connection stays only for the
  sandbox's own setup, the nonce and the after-the-fact checks.
- Check: a migration with `copy ... to program` and one with `copy ... to '<file>'` each exit 2
  naming the file and line, and neither creates anything on the host. These fail today.
- Check: everything that builds today still builds (`supabase_app`, extensions with and
  without schema, the starter `handle_new_user` trigger, the lab).
- Minor, same area: the search path is written in two places (`sandbox.py` `SEARCH_PATH` and
  the PostgREST literal); make it one.
