# T-06: An RLS oracle that does not guess from errors

Status: done
Risk: high (decides every `protected` verdict; runs migration-authored expressions)
Scenarios: S-2, S-4, S-5 (a `protected` verdict is only ever RLS's)
Depends on: T-04 (merged at eac2097 by the owner's decision on #8, option 1)
Areas: `rlsentry/attacker.py` (`_rls_answered` and its callers), `rlsentry/sandbox.py` (`Inspector`)

## Why
T-04 used up its three fix rounds on one question: was a refused write refused by
row-level security? Each round inferred the answer from the error PostgREST returned
(22xxx, then 42501, then a resend with ordinary triggers off), and the table's own code
could always produce the same error. The last verdict
(https://github.com/pitaya943/rlsentry-v2/pull/6#issuecomment-7116794096) left:
- **D7.** A 42501 from a CHECK, a domain CHECK, an `ENABLE ALWAYS` trigger, or a policy
  that reads `session_replication_role` reads `protected`, but anon can write.
  Cases: c42, c42proof, d42, a42, a42proof, r42, r42proof, uc42.
- **D8.** Genuinely protected tables exit 2 when an ordinary trigger shapes the row (fp1)
  or writes to another RLS table (fp2).
- **D9.** Mutants v1 (resend without JWT claims), v5 and v6 survive.
- **Unspecified.** Policies that read `request.method`, `request.headers` or `request.path`;
  the resend's claims lack `exp` and duplicate `channel.py`'s payload.

## What
Stop inferring. Decide "refused by RLS" from the policies themselves, so the class
disappears by construction:
- `protected` for an operation means: anon's effective policy for that operation is
  false (or null) for every row tried, as PostgreSQL combines them. That is permissive
  policies OR'd and restrictive AND'd, for roles anon/public, cmd = op or ALL, plus the
  table grant. Each row is evaluated as PostgreSQL checks it: for INSERT, the row after
  defaults and BEFORE ROW triggers; for UPDATE/DELETE, USING on the target row and WITH
  CHECK on the new row.
- The evaluation runs migration-authored expressions, so it runs only on the
  non-superuser `postgres` connection, as anon, with the same claims and request
  settings PostgREST sets (one shared source for the claims, `exp` included), in a
  rolled-back transaction, under the statement timeout. Never on the superuser
  connection.
- A refused write whose policy evaluates true is not `protected`: make room and retry
  as T-04 does, else exit 2 naming table and operation. A write refused by RLS on
  another table (fp2) is `protected`, with that table named in the basis.
- The REST attack stays the source of EXPOSED (D-2). The oracle only decides whether a
  refusal is RLS's; it never turns a refusal into EXPOSED. A policy that evaluates true
  while the REST write was refused gets the "neither" exit.

Recommended route (the builder may choose another and says why in the trail):
get the checked row with a rolled-back `INSERT ... RETURNING *` on the `postgres`
connection (BYPASSRLS, so BEFORE triggers run and RLS does not), then evaluate
`pg_get_expr(polwithcheck, polrelid)` and friends against that row as anon.
Remove the `session_replication_role` resend if it is no longer needed.
