# T-03: Real-project migrations and seeding

Status: open
Risk: high (the sandbox's data model: roles, auth stand-in)
Scenarios: S-6
Depends on: T-01
Areas: `rlsentry/sandbox.py` (auth stand-in, migration errors), `rlsentry/seed.py`

## What
Design §3 steps 3-5: `auth` schema with `auth.users`, `auth.uid()`, `auth.role()` and
`auth.jwt()` reading `request.jwt.claims`, the way Supabase defines them. Extensions `pgcrypto` and
`uuid-ossp`. Migrations applied one transaction each; on failure, name the file and the
missing object, tear down, exit 2. Seeding in FK order including `auth.users`, honouring
CHECK, enum and FK constraints. Rows that cannot be generated are skipped and noted in the
report.

## Check (fails today: no auth schema, simple seeding only)
- A fixture migrations folder written like a typical Supabase app (`profiles` with
  `id uuid references auth.users`, policies using `auth.uid()`, an enum column, a CHECK
  constraint, `todos` with an FK to `profiles`) builds, seeds every table and is attacked
  (exit 0 or 1, not 2).
- A folder whose migration uses `storage.buckets` exits 2 and the message names `storage`
  and the file.
- After that failure, no sandbox resources remain.
